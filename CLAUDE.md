Guidance for Claude Code working in this repository.

## Commands

```bash
npm run dev      # Vite dev server
npm run build    # tsc -b, then production build
npm run lint     # ESLint
npm run preview  # Serve the production build
npm run deploy   # Build + publish dist/ to GitHub Pages
```

No test runner. Run `npm run lint` and `npm run build` for meaningful changes. Pushes to `main` build and deploy via GitHub Actions. `VITE_DATA_BASE_URL` points the app at an alternate data source (defaults to the hosted scraper output).

## Architecture

Single-page React 19 + TypeScript + Vite app visualizing KVV train cancellations. Purely client-side: static JSON from the `kvv-ausfaelle-scraper` site is fetched and processed in the browser. Deployed to GitHub Pages, so `vite.config.ts` sets `base` to `/kvv-ausfaelle-viewer/`.

### Data flow

1. **`src/api.ts`** — fetch wrappers over `VITE_DATA_BASE_URL`. The remote data is a hierarchy: root `index.json` (discovery contract: `schemaVersion`, `years`, and the ordered public `causes` and `verificationStatuses` taxonomies) → `<year>/index.json` (per-line `files` + a `verification` summary, of which only `source` is read — tallies are recomputed locally so they follow the active filters) → `<year>/<file>` (`Cancellation[]`). `fetchNoticeText` loads an archived KVV notice body.

2. **`src/utils/rootIndex.ts`** — `parseRootIndex` validates the root instead of an unchecked `as RootIndex`: supported `schemaVersion` (1), a well-formed `causes` array (non-empty; non-empty `id`/`label`/`description`; unique ids; exactly one `unknown`) and, when published, `verificationStatuses` (same checks; may not claim the viewer-reserved `unchecked` id) — otherwise it throws a German-facing load error. `verificationStatuses` is **optional**: absent/null yields an empty list and the whole verification UI hides, so a stale cached root still loads. Shared shape check: `parseDefinitions`. Extra root fields are tolerated.

3. **`src/hooks/useKVVData.ts`** — the state machine. Three chained effects (root index → year index → selected line files), each guarded by `AbortController` and, for the data load, a `requestId` ref against stale responses. Line files are memoized in a `Map` ref keyed by `year/file`. Selecting a year selects all its line files. Outputs `rawData` (combined, date/time-sorted), `catalogs` (**`src/utils/catalogs.ts`** — `{ causes, verification }`, threaded as one prop rather than one per taxonomy; no module-global taxonomy state) and `verificationSource` (attribution only).

4. **`src/utils/filtering.ts`** — the compute core. `indexCancellations(data, catalogs)` pre-derives per-row search text (including resolved cause *and* verification labels, so both are searchable), time-of-day category, departure hour, day-of-week, and the resolved `cause`/`verification` keys once. `buildCancellationsView(indexed, filters, catalogs)` then does a single pass producing the filtered list **and** every aggregate (daily / line / departure stop / hour / day-of-week / cause / verification) plus `verificationSummary`. Three aggregates follow deliberate rules:
   - `toDailyStats` materializes a **continuous calendar** across the selection (a day with no announcement is a real `0`, not a gap — otherwise the bar rhythm and the mean average the wrong days) and attaches the trailing **7-day rolling mean** (`rolling`, null until the window is full).
   - `toHourStats` emits the full 0–23 histogram so empty night hours stay visible as gaps; `[]` when nothing in the selection has a `fromTime`.
   - `toStopStats` ranks departure stops, capped at 12.

   Filter counts drive the toolbar: `getDateFilterCount` (0–2), `getZeitFilterCount` (dates + Tageszeit + Wochentag — the "Zeitraum" expander badge, excluding the always-set year), `getAdvancedFilterCount` (search/cause/verification/Tageszeit/Wochentag), `getActiveFilterCount` (date + advanced — the inline reset label and `hasActiveFilters`). Reset restores `DEFAULT_CANCELLATION_FILTERS`, dates included. `App.tsx` wires both stages via `useMemo`, so indexing reruns only on `rawData` change.

5. **`src/utils/dateUtils.ts`** — time-of-day buckets (filter-only; the coarse aggregate is gone, superseded by the hour histogram), day-of-week categories, labels, chart ordering, `getHour`/`addDays`, and `matchesDayOfWeekFilter` (`weekday`/`weekend` are synthetic groupings, single days exact — see `src/types.ts`).

6. **`src/utils/causeUtils.ts`** — the **cause** ("Ursache") layer, driven entirely by the catalog the scraper publishes; there is **no** hard-coded cause union, label map or ordering in the viewer (a new scraper cause needs no viewer change). `buildCauseCatalog` turns validated `CauseDefinition[]` into `{ definitions in producer order, id → label }`. `resolveCauseId` maps blank/missing to the catalog's guaranteed `unknown`, keeping any non-empty id verbatim; `resolveCauseLabel` returns the catalog label, `Unbekannt`, or `Unbekannt (<id>)` for a drifted id — drift stays diagnosable, never silently collapsed. `getCauseOptions` / `toCauseStats` produce options and chart aggregates in catalog order. The ordering rule (catalog order, observed-but-uncatalogued ids spliced in lexically just before the fallback bucket) lives in **`src/utils/taxonomy.ts`** (`orderTaxonomyIds`, `buildLabelMap`, `TaxonomyDefinition`), shared with verification since both taxonomies share a shape.

7. **`src/utils/verificationUtils.ts`** — the realtime-**verification** ("Prüfung") layer. The scraper cross-checks announcements against `bahn.expert` and stores an advisory verdict; only a minority of trips are checked, so *absent* is normal, and a verdict never overrides the record's primary meaning (KVV announced a cancellation). The scraper's five statuses answer the producer's question ("what did the source see?"); the viewer asks the reader's — "was the announcement right?" — which has three answers, so **every surface speaks in `VERIFICATION_GROUPS`**: `confirmed` ("Ausfall bestätigt" = `cancelled` + `partial`), `contradicted` ("Fuhr trotz Meldung" = `ran`), `inconclusive` ("Kein Befund" = `no-data` + `unresolved` + `unchecked`). `no-data` is inconclusive deliberately: the source explicitly holding no information is epistemically the same as never having looked. `GROUP_BY_STATUS` maps known ids and `resolveVerificationGroup` falls back to `inconclusive`, so a later scraper status can never silently count as confirmation or contradiction.

   Unlike the cause layer this one hard-codes German display text (`GERMAN_STATUS_TEXT`, `VERIFICATION_GROUPS`) — the only taxonomy wording not taken from the producer — because the scraper publishes it in English; unmapped ids fall back to the published label. `UNCHECKED_STATUS_ID` (`unchecked`) is a **synthetic** bucket appended to every catalog for records with no verdict; `parseRootIndex` rejects that id from the producer so the two can't collide. `catalog.available` is false when no taxonomy is published, hiding the filter, chart, table column and summary tile rather than rendering empty shells. The view counts **raw statuses** (a group alone can't distinguish checked from unchecked); `toVerificationStats` rolls them into group order (`[]` when nothing carries a verdict, so the chart never degenerates into a lone "Kein Befund" bar) and `toVerificationSummary` yields the tile's `checked`/`confirmed` counts. The precise status survives in the table cell's tooltip and the CSV's `Prüfergebnis` column.

8. **`src/utils/dataTransforms.ts`** — small pure helpers: `lineFileToLabel` (`S1-S11.json` → label), `extractNoticeId`, `cleanNoticeText`. **`src/utils/csvExport.ts`** — client-side CSV of the filtered rows (UTF-8 BOM so Excel decodes German, localized Ursache, paired Prüfung (group) / Prüfergebnis (status) columns), wired to the table's "CSV exportieren".

## UI

`App.tsx` holds the only page state (`filters`) plus `useKVVData`/`useTheme`; everything in `src/components/` is presentational and prop-driven. `CancellationCharts` (Recharts) is `React.lazy` + Suspense to keep the initial bundle small. UI copy is German.

The design language is **KERN UX** via `@kern-ux-annex/kern-react-kit`. Its self-contained CSS (reset, tokens, light/dark themes, embedded Fira Sans, component styles) is imported once in `src/main.tsx`; `@kern-ux/native` is **not** used. Custom CSS uses the kit's current tokens — `--kern-color-layout-text-default`/`-muted`, `--kern-color-layout-border`, `--kern-color-layout-background-hued` (raised surfaces), `--kern-color-action-default`/`-on-default`, `--kern-metric-border-radius-*`. The older `--kern-color-decorative-*` / `*-background-default-surface` names from `@kern-ux/native` do not exist here.

**Page anatomy**: a **toolbar + canvas** layout. `AppHeader` (a KERN-styled band — *not* the federal `KernKopfzeile`, which would falsely imply an official site) with the "KVV" mark, title and theme toggle; then inside a `KernContainer` a sticky `ControlBar` over a single full-width canvas (`SummaryBar` → charts → collapsible table), and a footer with the data-source link. Everything wraps on mobile.

- **Progressive disclosure** is the organizing principle: the casual answer stays visible (stat strip + charts), only bulky controls recede. `ControlBar` = (1) one wrapping control line: `FiltersSection` grows to fill (`.filter-rail`, `flex: 1 1 16rem`, so the search `KernInput` expands while the Ursache/Prüfung selects stay compact), then a trailing group with the "Linien (n/m)" and "Zeitraum" toggles and the inline reset (only when `getActiveFilterCount > 0`); items share a bottom baseline (`align-items: flex-end`). (2) The open expander panel below it — `LinesSelector` or `TimeFilters` (year scope + date presets + Von/Bis + Tageszeit + Wochentag), opening one closes the other (`useState<"lines"|"zeit"|null>`). "Zeitraum" badges `getZeitFilterCount`; inline filters show their own value and need no badge. The table sits in a `KernAccordion`, collapsed by default (count + "gefiltert" in the title, CSV export in the body). No custom popovers — plain controlled state.
- `SummaryBar` is the result readout at the top of the canvas (rendered by `App.tsx`, only when `!loading && !error`): a wrapping row of `.summary__value` over `.summary__label` tiles — total first (`--primary`, large, brand-colored), then affected lines, strongest line, the verification tile (checked count over `Geprüft · <source> · n bestätigt`, only when the selection holds a verdict) and peak day. Tiles with no data are omitted.
- Cause / Prüfung / Tageszeit / Wochentag selects go through one generic `FilterSelect<T>` (a `KernSelect` over `{ value, label }[]` with a typed `onChange`), so a new select filter is a one-liner with no `as`-casts. The year keeps `YearSelector` (nullable + dynamic options); Von/Bis share a `DateField` helper inside `TimeFilters`.
- KERN components in use: `KernSelect`, `KernCheckbox` (line grid), `KernInput`, `KernButton` (date presets: active `primary` / inactive `tertiary`; toggles use `arrow-up`/`arrow-down` + `aria-expanded`), `KernAccordion`, `KernCard`, `KernTable`, `KernBadge`, `KernAlert`, `KernLoader`, `KernLink`, `KernHeading`, `KernText`, `KernContainer`. KERN form controls append "- Optional" unless `required` is set; always-valued filters pass `required` rather than CSS-hiding `.kern-label__optional`.
- **`KernCard` quirk**: it is `display:flex; align-items:flex-start`, so its body sizes to the *title width* and block content collapses. `App.css` overrides `.kern-card { align-items: stretch }` + `.kern-card__container { width: 100% }` — without this Recharts measures 0 width and renders nothing. `ChartCard` wraps card + optional description + `.chart-wrapper`.
- **Chart colors**: SVG `fill` can't resolve `var(--kern-…)` and `getComputedStyle` returns the unsubstituted chain. `useChartColors` assigns `color: var(--token, <fallback>)` to a probe element and reads the used color (the fallback matters — an unknown token would compute to the *inherited* color), re-resolved on theme change (hence `CancellationCharts` takes a `theme` prop). One color per chart; each chart carries a **single series**, so the hues are not a categorical scale. The exception is `dailyTrend`, plain `--kern-color-layout-text-default`, so the rolling mean reads as an annotation of the bars rather than a rival series.
- **Chart set** (render order): the daily trend runs full-width as a `ComposedChart` — bars plus the 7-day-mean `Line` (`connectNulls={false}`, so it starts a week in instead of faking a partial window) with a `Legend`, since two series can't be told apart by color alone; `minTickGap` de-crowds the date axis. Below it a responsive `.charts-row` grid of `BreakdownChart` bars: "Nach Linie", "Nach Ursache", "Nach Abfahrtsstunde", "Nach Starthaltestelle", "Nach Wochentag", "Nach Prüfung" last. The horizontal ones (Linie, Ursache, Starthaltestelle, Prüfung) turn their longer German labels sideways; Abfahrtsstunde (24 numeric ticks, `categoryInterval={1}`) and Wochentag stay vertical. `BreakdownChart` is the one parameterized component behind all of them — `categoryWidth`, `categoryInterval`, `truncateCategories` (stop names elide at 22 chars) are its only knobs. Abfahrtsstunde and Starthaltestelle hide themselves on empty stats; "Nach Prüfung" renders only when `verificationStats` is non-empty and carries the source attribution in its description.
- `KernTable` is data-driven and **rejects object cell values at runtime** — rich cells (two-line Von/Nach stops, the "KVV" source link, the Prüfung status dot) come from column `valueFormatter`s in `CancellationsTable.tsx`, with values packed by separator and unpacked there. The Prüfung column is spliced in only when `catalogs.verification.available`; it shows the **group** label so the row reads in the filter's and chart's vocabulary, the dot carries the only color (`.cell-verification--<group>`), and the precise status + German description are the cell's `title`.
- Two native elements are used where the KERN component's contract doesn't fit: the Von/Bis `<input type="date">` (`KernInputDate` is a 3-field fieldset whose change contract doesn't match ISO-string filters) and `NoticeDialog`'s `<dialog>` (KERN's dialog is context-driven with internal open state, unsuited to one dialog opened from arbitrary rows). Both are styled with KERN tokens. `NoticeDialog` lazily fetches an archived KVV notice by id, keyed so a stale response can't render against the current notice.
- `src/App.css` is **layout-only**; it and `src/index.css` use `--kern-*` tokens only (KERN's default text color is `--kern-color-layout-background-inverted`). There is no custom color palette.
- Theming: `useTheme` sets `data-kern-theme="light|dark"` on `<html>`, defaults to the OS preference and follows it live, with a manual toggle persisted in `localStorage`.
